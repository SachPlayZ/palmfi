How palmfi uses Chainlink CRE as the risk engine for treasury vaults

Assume an attacker can produce valid signatures. palmfi's Vault limits what any valid signature can move right now. Anything above the Instant budget waits, and CRE decides how long: two shared workflows score every request against that Vault's own onchain history and write a signed delay or a FLAG back through the Keystone forwarder.

01 · Why CRE

What we need from an offchain executor, and why CRE fits

No single trusted key

A decentralized verdict

If the risk engine were our own server, stealing its key would be the new single point of failure. A DON reaches consensus on each report and the forwarder checks the signatures before the Hub sees it.

Reacts to events

Log triggers on the Hub

Every Vault emits through one Hub, so one log trigger catches every RequestQueued, ConfigChange and pool Outflow across all orgs within a block.

Catches what was missed

Cron for liveness

A scheduled Reconciler scores anything the Sentinel missed, checks reserves and EIP-7702 delegations, and writes a heartbeat the Hub uses to know CRE is alive.

Too heavy for gas

Compute offchain, enforce onchain

The surprise model reads the last 32 outflows, destination counts, hours and wallet ages, then runs log/exp fixed-point math. CRE computes; the Vault only clamps and applies.

Private alerts

Confidential HTTP

Voters get a Telegram alert on long delays and FLAGs. The API key lives in Vault DON secrets and is injected inside the enclave, so workflow code never sees it.

Fits the 3-workflow limit

Two shared workflows

CRE allows 3 workflows per organisation, so we can't run one per Vault. Two shared workflows serve every Vault; each request is still scored against its own Vault's profile (ADR-0003).

04 · The model CRE runs

Deviation score: surprise in bits, mapped to time

The Sentinel asks one question: how surprising is this request, given this wallet's and this Vault's own history? It answers in bits of surprisal, scored at both wallet and Vault scope, and keeps the higher one. Everything is integer fixed point (bigint, milli-bits, table-based exp2, repeated-squaring log2) and measured at the request's own createdAt, so a late re-score by the Reconciler gives the same answer and every DON node signs identical bytes.

S = S_amount + S_dest + S_time + S_velocity + S_flags (max of wallet and Vault scope) delay = clamp( Floor · 2^(S / k), Floor, MaxDelay ) k = 2.5 bits per doubling quiet : amount ≤ usualMaxPayout and S < 2.5 bits → delay 0 (Vault honours it only within the Instant budget) FLAG : S ≥ S_flag (28 bits prod, 18 testnet) or blocklisted destination → freeze + blocklist blind : no baseline at all → MaxDelay (unsure means slow)
TermWhat it measuresRobustness detailReason code
S_amountLog-amount vs the Vault's executed historyMedian / MAD baseline, MAD floor of ±√2×; zero up to the onboarding threshold; profile seeds it until 8 samplesUNUSUAL_AMOUNT
S_dest−log₂ of a Laplace-smoothed destination frequencyOnboarding destinations get 8 pseudo-counts; all-time destinationCount vouches only at Vault scopeNEW_DESTINATION
S_timeHour-of-day surpriseBusiness hours from the profile get 2 pseudo-counts eachOFF_HOURS
S_velocityPoisson surprisal of the request rateRate measured over at least 7 days; catches bursts of small payments (smurfing)VELOCITY

Routine payroll scores about 3 bits and waits about 30 minutes. A $3M payment at 3am to a new address scores about 30 bits and is FLAGged. The baseline learns only from executed, un-vetoed outflows, with a per-day drift cap, so an attacker can't train it with vetoed requests.

06 · Trust boundaries

What CRE can and cannot do to a Vault

We designed so that CRE adds safety without becoming a new way to lose funds. A fully compromised workflow can make things slower or freeze a Vault, but it can't release more than the Instant budget.

Compromised CRE

Bounded by the Vault

The Vault clamps every delay to [Floor, MaxDelay], enforces CapDelay over the Hard cap, and honours delay 0 only within the remaining budget, which it spends. A malicious verdict releases no more than the budget.

CRE silent

Fails slow

Unscored requests wait MaxDelay. When the heartbeat goes stale, creLive() turns false and the plain budget lane resumes, so silence never lets more money out than before.

Replay safety

Hub never reverts on content

The forwarder only marks a report used if onReport succeeds. So the Hub reverts only on a wrong caller and drops bad content as ReportRejected(reason): expired, duplicate, hash mismatch, unknown vault, untrusted workflow (ADR-0005).

Identity

Pinned workflow

pinWorkflow fixes the forwarder plus workflow id, owner and name from report metadata. The testnet Hub trusts the simulation forwarder so judges can run cre workflow simulate --broadcast.

Determinism

Consensus-safe inputs

No floats, no randomness, no node clock. Time comes from the block header; nonces come from trigger data; Reconciler ordering breaks ties by vault then id so every node sorts the same way.

Missing data

Never freeze on a failed read

A failed reserves or delegation read is treated as no evidence. Without a block header the Sentinel writes nothing and leaves the request for the Reconciler.
